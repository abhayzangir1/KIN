# KIN Fresh Audit and Product Copy Review

**Audit date:** 2026-10-07
**Checkout reviewed:** main at 18e9a5c (remediation commit)
**Scope:** current source, existing documentation and public copy, and comparison against the supplied 33-item fix plan and the earlier audit.
**Change scope:** this report is documentation. No application logic was changed for this review.

## Executive summary

The new commit closes several real gaps from the earlier audit: task claim failures now abort execution, worktree setup fails closed for coding tasks, project branch settings reach merge, empty capabilities are denied by the old helper, credentials resolve by alias, provider streaming reaches the token callback in source, and model selection now uses a shared catalog in the add/edit agent views. EventLedger is initialized and records more lifecycle events. Direct terminal, browser, and desktop handlers now make Sentinel decisions.

The remediation is not complete. The highest-risk remaining defects concern task truth and approval binding:

1. **A task can be completed with evidence whose verified flag is false.** The completeTask repository method verifies that an evidence row exists by ID, but not that it is verified or belongs to the task/run. The normal completion path can write verified=0 and still call completeTask.
2. **The manual status endpoint fabricates a verified human sign-off.** A request to mark a task completed can create a human_signoff evidence row with an operator://signoff/... URI and verified=1, without recording a sign-off actor or content. The route also changes task state outside lease ownership.
3. **A worktree merge error is logged and execution can continue as success.** A commit hash is then used as verified evidence even when the commit was not merged into the project branch.
4. **Approval digests are supported but are not supplied on the normal approval-resolution path.** In addition, some direct desktop routes authorize one operation name/parameter set and execute another.
5. **Persistent queueing has a startup dispatch gap.** Startup admits a queued run and changes it to running, but discards the returned run instead of dispatching it.
6. **Provider readiness and model lists can be misleading.** Ollama is always reported configured and validated with two models even if it is offline. Hosted-provider readiness treats key presence as validation, and discovery fallbacks can be presented as configured after an API request fails.

The current source was reviewed, but no build, test suite, live provider call, fresh desktop package, or current end-to-end app session was run in this pass. The previous report records a scratch runtime pass from October 5; it is historical evidence for the earlier checkout, not verification of this commit. The signed-in browser profile was not available to this Codex session, so X, LinkedIn, and authenticated GitHub screens were not opened. Social and repository copy is provided as local drafts only.

The earlier detailed baseline remains in [KIN_COMPREHENSIVE_AUDIT_AND_FIX_PLAN.md](KIN_COMPREHENSIVE_AUDIT_AND_FIX_PLAN.md). This report supersedes its issue dispositions where the current checkout has changed.

- **Source confirmed:** directly visible in the current source or documentation.

- **Resolved in source:** the specific submitted issue appears addressed in the reviewed code. This does not mean runtime behavior was exercised.
- **Historical runtime evidence:** observed in the earlier isolated scratch run described in the previous report; not repeated against this commit.
- **Not demonstrated:** code exists, but current end-to-end behavior was not run in this audit.

The current report is based on source inspection. It does not claim that compilation, tests, model inference, browser/computer use, or clean-machine packaging passed.

## New and residual findings

### P1 — task evidence, completion, and authority

#### NEW-01 — Completion accepts unverified or unrelated evidence

**Evidence:** core/src/domain/task_repository.ts:325-344; core/src/server/core_server.ts:7856-7895.

The repository checks only whether an evidence row with the supplied ID exists. It does not require verified=1, the matching task_id, the matching run_id, or an evidence type allowed by the task's verification specification.

The automatic success path stores an artifact_hash row whose URI may be git://commit/<sha> or a SHA-256 of finalContent (falling back to the run ID). It sets verified=1 when a commit hash exists, or when actions exist and have no recorded errors. Those conditions do not prove that a required test/build/acceptance check passed. If action errors occurred, the path can set verified=0 and still call completeTask, which currently accepts the row.

**Impact:** the task DAG and goal status can say “completed” without verified acceptance evidence.

#### NEW-02 — Manual task completion creates synthetic verified sign-off

**Evidence:** core/src/server/core_server.ts:5025-5074.

PATCH /api/tasks/:id/status accepts status: completed. When no evidence ID is provided, it inserts a human_signoff row with URI operator://signoff/<taskId> and verified=1. The record does not include the signing user's identity, a confirmation record, a reason, or evidence of what was reviewed. The handler can first force a task into running, then complete it. It also changes a next-ready sibling task to running without claiming a worker lease.

The endpoint may be used by a human-facing UI, but the database record represents a verified sign-off that is stronger than the request data proves.

**Impact:** task state, goal completion, and downstream work can be advanced without a worker claim or a verifiable sign-off.

#### NEW-03 — Merge failure does not stop successful completion

**Evidence:** core/src/server/core_server.ts:7740-7758, followed by evidence creation at 7856-7895.

If verifyAndMerge returns an error, CoreServer logs a warning and continues. The worktree commit SHA is still available to the later completion path and can cause evidence to be marked verified. A failed merge can therefore be reported as a completed task even though the project branch did not receive the change.

**Impact:** the UI and task record may report success while the project branch is unchanged or conflicted.

### P1/P2 — approvals and privileged direct routes

#### NEW-04 — Main approval resolution does not bind the token to approved parameters

**Evidence:** core/src/security/sentinel.ts:66-139; core/src/server/core_server.ts:4658-4678; core/src/execution/tool_gateway.ts:126-153.

Sentinel can compute and verify a canonical parameter digest. However, the ordinary approval-resolution route calls generateApprovalToken(toolName, runId) without passing the approved payload. The resulting token contains no parameter digest. The route then executes the stored payload, which reduces exposure in that particular path, but the intended parameter-bound invariant is not actually enforced at the token layer.

#### NEW-05 — Direct desktop routes authorize a different action from the one executed

**Evidence:** core/src/server/core_server.ts:6030-6215.

The direct HTTP routes now call Sentinel, which is a meaningful improvement over bypassing it entirely. They still implement their own authorization mapping rather than using one shared action pipeline. For example:

- App launch evaluates launchApp with target and args, but the approval record is created as desktopLaunchApp.
- The desktop-interact route evaluates every request as desktopMouseMove, regardless of whether the body asks for click, move, text entry, or a key press; the approval record is named desktopInteract.

The tool name and parameters covered by the approval should exactly match the controller operation and payload that will execute. This mismatch can produce wrong risk treatment or an approval record that cannot faithfully describe the action.

**Disposition of old finding:** the claim that these routes all bypass Sentinel is stale for this checkout. The remaining issue is inconsistent, action-mismatched enforcement, not complete absence of checks.

### P2 — run lifecycle, provider discovery, and event authority

#### NEW-06 — Startup admits a queued run but does not dispatch it

**Evidence:** core/src/server/core_server.ts:298-303; queue admission in core/src/kernel/agent_kernel.ts:134-153.

At startup, CoreServer calls admitNextQueuedRun() and discards the returned AgentRun. Admission transitions the run to running; the startup path does not enqueue it for execution. The later normal completion path does dispatch an admitted run, but that handler is not running when startup performs this admission.

**Impact:** a previously queued run can be marked active without being started. Recovery may later classify it as stale, but that is not equivalent to executing it.

#### NEW-07 — Readiness reports configured/validated without checking availability

**Evidence:** core/src/execution/model_gateway.ts:124-145; Ollama discovery fallback at 150-196 and provider fallback paths below it.

getProviderReadiness('ollama') always returns configured=true, validated=true, and modelCount=2. When Ollama cannot be reached, fetchProviderModels returns fixed Ollama model IDs with both flags true. For hosted providers, readiness treats a decryptable key as validated and uses a fixed model count rather than a successful provider validation or catalog count.

**Impact:** the settings/UI can show a local runtime or hosted credential as ready when it is offline, invalid, unauthorized, or has no usable models.

#### NEW-08 — Model discovery still includes fallback catalogs and lacks free/paid filtering

**Evidence:** core/src/server/core_server.ts:1538-1587; core/src/execution/model_gateway.ts:150-196 and provider fallback handlers; ui/src/components/SettingsModal.tsx:447-475.

The models endpoint loads stored rows, queries active credentials, and—if the resulting list is empty—fetches a default OpenRouter catalog even when no OpenRouter credential is configured. The API includes readiness fields, and the agent selectors filter some unconfigured rows, but this is not the requested single credential-driven catalog. Provider-specific fallback lists can also remain selectable or be marked ready based on key presence rather than successful discovery.

OpenRouter rows expose an isFree field, but the UI does not provide a complete dynamic free/paid filter. Settings includes a curated free-model list rather than a unified filter over the live catalog.

**Impact:** users can see model options that are not validated or available to their account. Missing keys do not necessarily cause an exception, but catalog contents and readiness are not a faithful inventory of configured, usable choices.

#### NEW-09 — “Zero Cost” and “No Quota Burn” labels are unsupported

**Evidence:** ui/src/components/AddAgentModal.tsx:232, ui/src/components/AgentInspector.tsx:1492, ui/src/components/SettingsModal.tsx:452-455; OpenRouter credential seed at core/src/server/core_server.ts:226-239.

The selectors call entries “Zero Cost”; Settings can display “Zero Cost • No Quota Burn”; an environment key may be seeded with alias “OpenRouter Free Tier (ZDR Compliant)”. The source does not establish that a provider will keep a model free, that account-level quotas will not apply, or that a model is ZDR-compliant for this user/account. Zero prompt/completion pricing metadata is not a guarantee of availability or billing outcome.

#### NEW-10 — EventLedger is in use but not authoritative

**Evidence:** core/src/security/event_ledger.ts; direct fallback writes in core/src/kernel/agent_kernel.ts:445-460 and core/src/communication/channel_service.ts:61-80.

The ledger is initialized and used by CoreServer, AgentKernel, and ChannelService. When ledger recording fails, some writers fall back to direct SQL inserts into event_journal; those fallback payloads do not go through EventLedger's sanitization. Direct writes also remain, so it is not yet a single authoritative event path.

**Disposition of old finding:** improved from “not wired” to “partially wired; authority and fallback sanitization remain open.”

### P2/P3 — leases, context, integrations, and product truth

#### NEW-11 — Lease supervision still does not cover every long operation

**Evidence:** initial task lease at core/src/server/core_server.ts:7256; model-call watchdog in core/src/kernel/agent_loop.ts:328-354; renewal callback near core/src/server/core_server.ts:7542.

Claim failure now aborts the run, and a watchdog heartbeats/renews while the model invocation is active. The initial task lease remains 120 seconds. The watchdog has a ten-minute ceiling, renewal results are ignored, and long tool operations do not use the same renewal loop. A long-running action can still lose ownership without the worker acting on that loss.

#### NEW-12 — Context compaction now includes some project state but remains partly synthetic

**Evidence:** core/src/kernel/agent_loop.ts:174-270.

The current compaction input includes modified file paths derived from successful write actions, pending tasks from the repository, and persisted decisions. It still synthesizes message IDs, task/action labels, and generic “fix applied” descriptions; the active task/goal identity can fall back to a run or task ID. This is progress, not a complete snapshot of verified project state.

#### NEW-13 — The browser still launches Chromium with sandboxing disabled

**Evidence:** core/src/browser/browser_controller.ts:228.

The flag remains present. A Git worktree is not an OS sandbox, and disabling Chromium's sandbox means the browser should not be described as isolated from the host.

#### NEW-14 — Demo/example code returns fabricated success-shaped data

**Evidence:** docs/EXAMPLES/daily-briefing-bot/implementation.ts; docs/EXAMPLES/research-analyzer/implementation.ts.

The daily briefing example returns fixed counts and “All services operational.” The research analyzer returns canned “Verified” findings and recommendations without fetching or analyzing source material. The examples should be described as illustrative scaffolds, not runnable integrations or actual measured results.

#### NEW-15 — Public release and repository version descriptions disagree

**Evidence:** root and workspace package metadata use version 1.0.0; the [public release page](https://github.com/abhayzangir1/KIN/releases/tag/v0.1.0) is tagged v0.1.0; the old README hard-coded installer names and claims that those assets were standalone/verified.

The new README links only to the release index and does not promise specific asset names. Before announcing a desktop download, reconcile versioning and verify the exact files and a clean-machine installation.

#### NEW-16 — Old documentation links and claims were not portable or evidence-based

**Evidence:** the former README and docs/TUTORIALS.md, docs/FAQ.md, docs/ARCHITECTURE.md, docs/PRD.md, and docs/TRD.md.

The old public copy included competitor privacy/pricing claims, absolute “zero telemetry/offline/exact recovery” promises, stale test counts, unsupported package claims, screenshots captioned as proof of runtime behavior, tutorial links using file:///d:/KIN/..., and a FAQ claiming LAN access even though the core binds to 127.0.0.1.

The README and selected documentation entry points were rewritten or qualified in this change. The detailed PRD/TRD remain design documents and require implementation-status reconciliation before being read as a feature inventory.

## Requested OpenCode-style model system

The desired product behavior is a useful target: store only keys the user supplies; discover models for configured providers; let the user filter OpenRouter models by free/paid using current provider metadata; show local Ollama models only when discovered; present the same selectable catalog for every agent; and keep an unconfigured provider from breaking another provider or local use.

KIN has pieces of this flow, but should not yet be described as having OpenCode-equivalent dynamic discovery. The current gaps are:

- Readiness is a hard-coded status calculation, not a successful authentication/catalog test.
- Ollama has hard-coded fallback model IDs marked validated even when its API is unreachable.
- Hosted providers can fall back to curated catalogs after errors and mark those models configured/validated based on key presence.
- The global catalog can request OpenRouter's public catalog when no provider models were otherwise found.
- OpenRouter isFree metadata exists, but the UI lacks a complete live free/paid filter and displays cost/quota certainty it cannot guarantee.
- Shared add/edit agent selection is a real improvement; Settings still has a separate curated free-model presentation.
- No provider inference was performed during this audit.

For product-pattern reference, OpenCode's current [provider documentation](https://github.com/anomalyco/opencode/blob/dev/packages/web/src/content/docs/providers.mdx) describes connecting provider credentials and selecting models, and its [model documentation](https://github.com/anomalyco/opencode/blob/dev/packages/web/src/content/docs/models.mdx) describes the model-selection workflow. The requested v2 tree could not be fetched in this audit; these links are reference material only and do not establish feature parity or current KIN behavior.

## Recommended repair order

1. Make task completion depend on evidence that is verified, task/run-bound, and compliant with an explicit acceptance rule. Remove fabricated sign-off records and stop direct task-status mutation from claiming worker-owned states.
2. Treat worktree merge failure, evidence persistence failure, failed verification, and lease loss as run/task failure; do not announce success.
3. Bind approvals to the exact canonical action payload on every creation and execution path. Use one authorization service for UI, HTTP, agent, schedule, recovery, and MCP actions.
4. Repair startup queue dispatch and define queued/running recovery transitions. Renew leases across long tools and stop work when renewal fails.
5. Make provider state truthful: configured, authenticated, reachable, discovered, and callable must be separate statuses. Remove unavailable fallback rows from selectable catalogs. Add one OpenRouter free/paid filter with pricing metadata labeled as provider-reported and subject to change.
6. Make EventLedger the single sanitized event writer; do not fall back to direct unsanitized SQL.
7. Use a real isolation boundary for untrusted shell, skill, MCP, and browser execution, or label the current boundary as process routing/worktree separation.
8. Re-run a clean build, targeted tests, provider calls with valid/invalid/no keys, queue restart checks, task/evidence state tests, HTTP approval tests, and fresh-machine packaging before making reliability claims.
9. Reconcile public version/release metadata and verify each downloadable asset before release promotion.
